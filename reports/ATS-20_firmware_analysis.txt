АНАЛИЗ ПРОШИВКИ ATS-20
Цель: повышение скорости и качества работы, возможность создания нового UI

КРАТКИЙ ВЫВОД

ATS_EX v1.18 можно существенно улучшить по скорости и качеству работы, а новый UI сделать реально. Основное ограничение аппаратной платформы: ATmega328P, около 32 KB Flash и 2 KB SRAM.

Новый UI не стоит строить поверх существующей системы showStatus()/showFrequency()/show...(). Сначала необходимо разгрузить архитектуру, отделить Radio Core от UI, перейти к событийной модели с частичной перерисовкой, оптимизировать I2C и encoder, а затем проектировать интерфейс.

1. ТЕКУЩАЯ АРХИТЕКТУРА

Сейчас проект представляет собой достаточно крупный монолит:

    ATS_EX.ino
         |
    +----+-----------+-----------+
    |                |           |
  Radio            Input/UI   Storage
    |                |           |
  SI4735          Encoder      EEPROM
                 Buttons
    +----------------+-----------+
                     |
                  main loop

UI, обработка радиочипа, input handling и persistence выполняются в одном основном execution loop.

Для ATmega328P это допустимо, но для действительно отзывчивого интерфейса это уже архитектурный потолок.

2. ОСНОВНАЯ ПРОБЛЕМА ПРОИЗВОДИТЕЛЬНОСТИ: I2C + OLED

UI активно пишет непосредственно в OLED. Используются отдельные функции вроде:

    showFrequency()
    showModulation()
    showStep()
    showBandwidth()
    showCharge()
    showVolume()
    showSMeter()
    showRDS()

При изменении состояния могут выполняться несколько независимых OLED-операций.

Это особенно неприятно для:
- вращения encoder;
- частого изменения частоты;
- S-meter;
- RDS;
- переходов между режимами.

В проекте для SSB patch применяется ускоренный I2C:

    g_si4735.setI2CFastModeCustom(500000);

после чего режим возвращается к стандартному:

    g_si4735.setI2CStandardMode();

То есть максимальная скорость I2C применяется локально, а OLED остаётся отдельным потребителем шины.

РЕКОМЕНДАЦИЯ

Ввести framebuffer/dirty-region подход, но с учётом ограничений SRAM.

Не:

    encoder
      -> showFrequency()
      -> OLED

а:

    encoder
      -> Radio State changed
      -> UI invalidation
      -> UI renderer
      -> минимальный I2C update

Например:

    enum UiDirty : uint8_t {
        UI_NONE       = 0,
        UI_FREQUENCY  = 1 << 0,
        UI_MODE       = 1 << 1,
        UI_STEP       = 1 << 2,
        UI_BANDWIDTH  = 1 << 3,
        UI_VOLUME     = 1 << 4,
        UI_SIGNAL     = 1 << 5,
        UI_RDS        = 1 << 6,
        UI_STATUS     = 1 << 7
    };

Изменение частоты должно означать установку dirty-флага, а не немедленную полную перерисовку.

3. ENCODER

Использование:

    volatile int8_t g_encoderCount = 0;

и:

    #define ENCODER_MAX_BURST 20

является хорошим решением.

Быстрый поворот encoder можно агрегировать:

    tick tick tick tick
          |
       +5 pending
          |
        loop()

Вместо потери промежуточных событий.

РЕКОМЕНДАЦИЯ

ISR должен быть максимально коротким:

- прочитать pins;
- декодировать состояние;
- изменить counter;
- выйти.

Никакого UI, Radio API, EEPROM, I2C и другой тяжёлой логики внутри interrupt context.

4. ROTARY.CPP: ЛОЖНАЯ АБСТРАКЦИЯ

Конструктор Rotary принимает pin1/pin2, но process() фактически захардкожен на D2/D3 через PIND.

То есть:

    Rotary::Rotary(char _pin1, char _pin2)

создаёт впечатление универсального класса, но process() работает только с конкретными физическими пинами.

Для текущего ATS-20 это работает, однако для новой архитектуры это необходимо исправить.

5. BLOCKING DELAY()

В main loop встречаются delay(), включая:

    delay(MIN_ELAPSED_TIME);

при:

    #define MIN_ELAPSED_TIME 100

Это может искусственно блокировать обработку интерфейса примерно на 100 ms.

Есть также короткие delay() в seek/display logic.

Startup delay() не является серьёзной проблемой, но интерактивные delay() необходимо убрать.

РЕКОМЕНДАЦИЯ

Заменить delay() на timestamp/deadline-based scheduling:

    if (millis() - lastAction >= 100) {
        ...
    }

Тогда одновременно смогут обслуживаться:
- encoder;
- OLED;
- RDS;
- receiver;
- buttons.

6. FREQUENCY TUNING

Текущая логика:

    if (frequencyRecentlyUpdated && g_encoderCount != 0)
    {
        doFrequencyTune();
        g_encoderCount = 0;
        return;
    }

уже пытается агрегировать изменения частоты.

Это правильная идея.

Но её можно развить до модели:

    requestedFrequency
    appliedFrequency

Например:

    encoder:
      7100
      7101
      7102
      7103
      7104

    UI сразу показывает 7104

    SI4735 получает 7104 после короткого settle window.

Это называется optimistic UI + deferred hardware commit.

Результат: энкодер ощущается практически мгновенным, а SI4735 не получает команду на каждый тик.

7. SSB TUNING

Текущая реализация BFO и виртуальной настройки является сильной частью прошивки.

Использование:

    g_currentBFO

и диапазона BFO позволяет реализовать:

    hardware frequency + BFO
             |
      virtual continuous tuning

Эту логику нужно сохранить, но вынести из ATS_EX.ino в отдельный radio/tuning модуль.

Например:

    tuning.step(+1);
    tuning.step(-1);
    tuning.getDisplayFrequency();
    tuning.commit();

UI не должен знать, что внутри используется BFO.

8. S-METER

Текущий S-meter вызывает:

    g_si4735.getCurrentReceivedSignalQuality();
    g_si4735.getCurrentRSSI();

после чего выполняет множество OLED операций.

Обновление порядка 10 раз в секунду само по себе нормально, но UI/I2C нагрузку необходимо ограничить.

РЕКОМЕНДАЦИЯ

Разделить:

    radio signal sampling: 10 Hz
    UI rendering:          5 Hz
    OLED update:           только если значение изменилось

Добавить hysteresis, чтобы небольшие колебания RSSI не вызывали визуальное дрожание индикатора.

9. RDS

RDS сейчас встроен непосредственно в main loop.

Архитектурно лучше:

    RDS decoder
         |
      RDS state
         |
      UI event

Например хранить компактное состояние:

    station
    radioText
    program
    synced
    errorLevel

UI должен только отображать состояние, а не управлять процессом RDS.

Это позволит сделать нормальный экран с частотой, названием станции и RadioText без связи UI с Radio Core.

10. EEPROM

Использование:

    EEPROM.update()

является правильным решением, так как байт не переписывается при неизменившемся значении.

Но для будущего UI и новых настроек лучше перейти к versioned configuration:

    struct Config {
        uint8_t version;
        uint8_t volume;
        uint8_t band;
        uint8_t mode;
        ...
        uint16_t crc;
    };

Схема:

    magic
    version
    payload
    CRC16

Это упростит развитие прошивки и защитит от повреждения/несовместимости конфигурации.

11. ОГРАНИЧЕНИЕ SRAM

ATmega328P имеет всего 2 KB SRAM.

Поэтому классический framebuffer:

    uint8_t framebuffer[1024];

съедает около половины всей доступной SRAM.

После этого остаются:
- RDS buffers;
- SI4735 state;
- settings;
- stack;
- временные buffers.

Поэтому полный framebuffer я не рекомендую.

РЕКОМЕНДАЦИЯ

Использовать tile/dirty rendering.

OLED 128x64 логически разделить на области и обновлять только изменившиеся области.

Это даст преимущества framebuffer-подхода без необходимости хранить полный экран в SRAM.

12. НОВЫЙ UI РЕАЛЕН

Но не следует пытаться сделать «смартфон на OLED».

ATS-20 имеет:
- маленький OLED;
- физические кнопки;
- один encoder;
- ограниченный CPU;
- 2 KB RAM.

UI должен быть инструментальным, а не мобильным.

Основной экран может содержать:

    +------------------------------+
    | USB      FM          STEREO  |
    |                              |
    |       103.700 MHz            |
    |                              |
    |       RADIO NAME             |
    |                              |
    | S7 ███████████░░░░  VOL 28  |
    | STEP 100k     BW AUTO        |
    +------------------------------+

Постоянно отображаются только Primary-параметры:
- mode;
- frequency;
- signal;
- volume.

Secondary-параметры показываются при изменении:
- step;
- bandwidth;
- ATT;
- BFO;
- RDS.

Например после изменения STEP:

    7100 kHz

    STEP 100 Hz

Через короткий timeout возвращается обычный основной экран.

Это позволяет получить чистый интерфейс без постоянного визуального шума.

13. СИСТЕМА МЕНЮ

Текущий подход вроде:

    ATT 10       SM 20
    SVC ON       SYN OFF
    DeE 75       AVC 46

эффективен с точки зрения Flash, но плохо масштабируется для пользователя.

Предпочтительнее:

    SETTINGS

    > Reception
      Audio
      Display
      Tuning
      RDS
      System

и:

    RECEPTION

    > AGC
      Soft Mute
      AVC
      SSB Sync
      SSB Filter

При этом реализация должна оставаться компактной: статические таблицы и небольшое state machine, без тяжёлой динамической системы меню.

14. FLASH

README и исходники указывают, что проект уже близок к пределу Flash.

Проект уже использует:

    LinkTimeOptimization
    Optimization = MinSize

и содержит комментарии о ручной экономии Flash.

Поэтому новый UI нельзя просто добавить поверх существующего кода.

Необходим Flash budget.

Нужно отдельно учитывать:
- Radio Core;
- UI renderer;
- strings;
- RDS;
- settings;
- SSB patch;
- библиотеки.

15. ЧТО МОЖНО ОПТИМИЗИРОВАТЬ В FLASH

Кандидаты:

1. Дублирование UI-функций:
   showFrequency()
   showModulation()
   showStep()
   showBandwidth()
   showCharge()
   showVolume()
   showSMeter()
   showRDS()

2. Дублирование button callbacks:
   simpleEvent()
   stepEvent()
   agcEvent()
   bandEvent()
   volumeEvent()

3. Постоянные строки.

Все подходящие строки необходимо систематически проверять на хранение во Flash через F() / PROGMEM.

4. Типы строковых указателей.

Например:

    char* bandTags[]

лучше заменить на:

    const char* const ...

и при необходимости использовать PROGMEM.

16. SI4735 API И РЕАЛЬНАЯ СКОРОСТЬ

Нельзя путать CPU speed с общей скоростью работы радио.

Команда:

    g_si4735.setFrequency(...)

зависит от:
- I2C;
- времени обработки SI4735;
- внутренних DSP операций;
- command/status protocol.

Поэтому простое увеличение частоты CPU не решает проблему responsiveness.

Наибольший эффект дадут:

    encoder aggregation
    +
    deferred SI4735 tuning
    +
    fast I2C where safe
    +
    minimal OLED traffic

17. I2C

SSB patch использует 500 kHz:

    g_si4735.setI2CFastModeCustom(500000);

При этом в исходниках присутствует комментарий о том, что безопасность режима не полностью подтверждена.

Это место необходимо измерить отдельно:

    100 kHz
    400 kHz
    500 kHz

для:
- frequency tuning;
- SI4735 commands;
- OLED updates;
- SSB patch download.

Если аппаратная конфигурация стабильно поддерживает 400 kHz, уже это даст заметный выигрыш.

19. MAIN LOOP

Главный loop должен приблизиться к:

    void loop()
    {
        inputTask();
        radioTask();
        rdsTask();
        uiTask();
        storageTask();
    }

Каждая задача должна быть:
- non-blocking;
- короткой;
- deterministic;
- без delay().

20. EVENT BUS

Вместо прямой связи кнопки с UI:

    switchCommand(&g_cmdStep, showStep);

лучше использовать компактное состояние событий:

    uint8_t pendingEvents;

Например:

    EVENT_FREQ_CHANGED  = 1 << 0
    EVENT_MODE_CHANGED  = 1 << 1
    EVENT_VOLUME_CHANGED = 1 << 2
    ...

Полноценную очередь событий в SRAM делать не нужно.

21. ЦЕЛЕВЫЕ ПОКАЗАТЕЛИ

Input latency:
    encoder -> изменение цифр
    цель: < 20 ms

UI latency:
    кнопка -> визуальная реакция
    цель: < 30 ms

Frequency hardware commit:
    encoder burst -> SI4735
    цель: примерно 30-70 ms после последнего изменения,
    если немедленный commit не требуется.

S-meter:
    5-10 Hz

RDS:
    асинхронное обновление

EEPROM:
    запись только после idle timeout
    и только изменившихся параметров.

ЗАКЛЮЧЕНИЕ

Это не плохая прошивка. Напротив, в ней видно понимание ограничений AVR и уже сделаны хорошие низкоуровневые оптимизации.

Сильные стороны:
- encoder burst accumulation;
- SSB virtual tuning через BFO;
- частичная перерисовка частоты;
- EEPROM.update();
- direct AVR register access там, где это оправдано;
- LTO + size optimization.

Основная проблема не в том, что код принципиально медленный. Он достиг архитектурного предела первоначального дизайна.

Для новой версии нужно не просто «добавить красивый UI», а построить компактную embedded UI architecture:

    Input
      ↓
    State/Event
      ↓
    Radio Core      UI Core
      ↓               ↓
    SI4735        Dirty Renderer
                      ↓
                    OLED

Главная стратегия:

    1. Убрать blocking delay()
    2. Encoder burst + deferred SI4735 tuning
    3. Dirty UI rendering
    4. Снизить количество OLED I2C transactions
    5. Разнести RDS/S-meter от tuning path
    6. Оптимизировать SI4735 I2C
    7. Провести Flash/RAM cleanup
    8. Только после этого финализировать новый UI

Новый UI для ATS-20 реален. Более того, при правильной архитектуре он способен не только улучшить внешний вид, но и повысить субъективную скорость работы приёмника.
