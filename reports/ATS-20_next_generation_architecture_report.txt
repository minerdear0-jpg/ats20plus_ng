ATS-20 NEXT GENERATION FIRMWARE
Уточняющий технический отчёт

Тема:
Можно ли на существующем старом железе ATS-20 получить существенно более быстрый SDR-подобный приёмник с качественным и приятным UI за счёт новой архитектуры ПО?

1. КРАТКИЙ ВЫВОД

Да.

Но важно правильно сформулировать результат.

Новая архитектура не превратит ATmega328P в современный мощный DSP-компьютер. Мы не получим широкополосный IQ SDR, тяжёлый программный DSP или большой FFT на самом микроконтроллере.

Однако на существующем железе ATS-20 вполне реально получить:

- существенно более быстрый tuning;
- практически мгновенную реакцию encoder;
- плавную SSB-настройку;
- более стабильный S-meter;
- RDS без заметного влияния на управление;
- быстрый OLED UI;
- контекстные меню;
- более понятную систему настроек;
- существенно более приятное ощущение устройства в руках.

Иными словами:

Новая прошивка может сделать старое железо ощущаемо устройством другого поколения.

2. ВАЖНОЕ РАЗДЕЛЕНИЕ: ВЫЧИСЛИТЕЛЬНАЯ МОЩНОСТЬ И ОТЗЫВЧИВОСТЬ

Основная ошибка при оценке такого проекта — считать, что скорость устройства определяется только частотой CPU.

В реальности:

    CPU speed
        !=
    device responsiveness

ATS-20 может иметь ограниченную вычислительную мощность, но при правильной архитектуре ощущаться очень быстрым.

Нужно оптимизировать не только количество инструкций, а latency всей цепочки:

    INPUT LATENCY
          ↓
    STATE UPDATE LATENCY
          ↓
    RADIO COMMAND LATENCY
          ↓
    DISPLAY LATENCY

Если эти четыре этапа короткие и предсказуемые, пользователь воспринимает устройство как быстрое.

3. ЧТО СЕЙЧАС ПРОИСХОДИТ

Текущая архитектура фактически заставляет несколько подсистем конкурировать внутри одного main loop:

    Encoder
       ↓
    Radio
       ↓
    SI4735
       ↓
    OLED
       ↓
    RDS
       ↓
    S-meter
       ↓
    Buttons
       ↓
    delay()

Проблема не обязательно в том, что каждая отдельная операция медленная.

Проблема в том, что они связаны между собой и могут блокировать друг друга.

4. ЦЕЛЕВАЯ АРХИТЕКТУРА

Новая архитектура должна выглядеть примерно так:

                     INPUT
                encoder / keys
                      |
                      v
                EVENT / STATE
                      |
          +-----------+-----------+
          |                       |
          v                       v
      RADIO CORE               UI CORE
          |                       |
      SI4735                 state/overlay
      tuning                 dirty regions
      BFO                    renderer
      RDS                        |
          |                       v
          +-----------------> OLED/I2C

Ключевой принцип:

UI не должен блокировать Radio Core.

Radio Core не должен знать детали отображения.

Input не должен напрямую вызывать OLED rendering.

5. ENCODER ДОЛЖЕН ОЩУЩАТЬСЯ МГНОВЕННЫМ

Для пользователя самое заметное действие — вращение encoder.

Нужно получить модель:

    физический encoder
           ↓
       event
           ↓
    local frequency state
           ↓
      OLED update
           ↓
    deferred SI4735 commit

То есть UI может немедленно показать новое значение, а физический radio chip получает итоговую частоту после короткого settle window.

Пример:

    encoder:
      7100
      7101
      7102
      7103
      7104

Пользователь сразу видит:

      7104

SI4735 при этом не обязан получать пять отдельных команд.

6. DEFERRED HARDWARE COMMIT

Это один из наиболее важных архитектурных приёмов для новой версии.

Нужно разделить:

    requestedFrequency
    appliedFrequency

requestedFrequency — что сейчас хочет пользователь.

appliedFrequency — что уже реально установлено в SI4735.

При быстром вращении:

    requestedFrequency
        меняется мгновенно

    appliedFrequency
        обновляется оптимизированно

Это уменьшает нагрузку на I2C и SI4735 и одновременно повышает субъективную скорость интерфейса.

7. SSB

SSB tuning является одной из сильных сторон существующей прошивки.

Сочетание hardware frequency и BFO позволяет получить виртуальную непрерывную настройку:

    hardware frequency
            +
           BFO
            |
            v
    virtual continuous frequency

Эту механику необходимо сохранить.

Но её следует вынести в Radio/Tuning Core.

UI не должен знать, что внутри используется BFO.

UI должен работать с абстракцией:

    tuning.step(+1)
    tuning.step(-1)
    tuning.getDisplayFrequency()
    tuning.commit()

8. НОВЫЙ UI НЕ ДОЛЖЕН БЫТЬ "СМАРТФОНОМ НА OLED"

Аппаратные ограничения:

    ATmega328P
    16 MHz
    32 KB Flash
    2 KB SRAM

означают, что интерфейс должен быть специально спроектирован для embedded-среды.

Цель:

не максимум графики,

а максимум понятности и отзывчивости.

Хороший UI должен делать меньше, но делать это мгновенно и предсказуемо.

9. КОНЦЕПЦИЯ ОСНОВНОГО ЭКРАНА

Например:

    +------------------------------+
    | FM                    STEREO |
    |                              |
    |        103.700 MHz           |
    |                              |
    |        RADIO XYZ             |
    |                              |
    | S7  ███████████░░     VOL 28 |
    |                              |
    | STEP 100k          BW AUTO   |
    +------------------------------+

Постоянно отображаются только основные параметры:

- MODE
- FREQUENCY
- SIGNAL
- VOLUME

Второстепенные параметры показываются контекстно:

- STEP
- BANDWIDTH
- ATT
- BFO
- RDS

Это позволяет не перегружать экран.

10. КОНТЕКСТНЫЙ UI

Например, пользователь изменяет STEP.

Во время действия:

      7100 kHz

      STEP 100 Hz

Через короткое время overlay исчезает и возвращается основной экран.

Другой пример:

Нажатие MODE:

          MODE

       FM
       USB
    >  LSB
       AM
       CW

После выбора:

          LSB

Основной экран снова появляется автоматически.

Такой интерфейс значительно лучше подходит для физического радиоприёмника, чем постоянное отображение десятков параметров.

11. ЧТО ОЗНАЧАЕТ "БЫСТРЫЙ SDR" В ДАННОМ КОНТЕКСТЕ

Термин SDR необходимо использовать аккуратно.

Если под SDR понимать:

- широкополосный IQ;
- программный DSP;
- большие FFT;
- сложную программную демодуляцию;

то старое железо этого не даст.

Но если под SDR понимать:

- программно управляемый многорежимный радиоприёмник;
- программный tuning;
- BFO;
- фильтры;
- AGC;
- RDS;
- программно управляемые режимы;
- гибкий пользовательский интерфейс;

то ATS-20 вполне можно довести до очень качественного SDR-подобного устройства.

Основная RF/DSP работа по-прежнему выполняется SI4735.

12. ПОЧЕМУ СТАРОЕ ЖЕЛЕЗО ЗДЕСЬ ДАЖЕ ИНТЕРЕСНО

Ограничения платформы заставляют решить проблему архитектурой, а не грубой вычислительной мощностью.

Нельзя просто добавить:

- больше RAM;
- более быстрый CPU;
- GPU;
- большой framebuffer;
- сложный UI framework.

Следовательно, необходимо:

- минимизировать latency;
- убрать blocking operations;
- агрегировать события;
- обновлять только изменившиеся области;
- планировать I2C;
- отделять hardware state от display state;
- экономить SRAM;
- экономить Flash.

Это классическая задача хорошего embedded engineering.

13. UI МОЖЕТ УЛУЧШИТЬ НЕ ТОЛЬКО ВНЕШНИЙ ВИД, НО И СКОРОСТЬ

Это принципиально важно.

Если UI построен вокруг dirty regions и event-driven state, он перестаёт быть источником задержек.

Вместо:

    event
      ↓
    redraw everything
      ↓
    OLED transfer
      ↓
    continue

получаем:

    event
      ↓
    update state
      ↓
    mark dirty region
      ↓
    continue radio work
      ↓
    minimal OLED update

Таким образом, хороший UI становится частью performance architecture.

14. S-METER

S-meter не должен вмешиваться в tuning.

Рекомендуемая модель:

    signal sampling: 5-10 Hz
    UI rendering:    около 5 Hz
    OLED update:     только при изменении значения

Добавляется hysteresis, чтобы небольшие изменения RSSI не создавали визуальное дрожание.

15. RDS

RDS также должен работать независимо от UI.

Правильная схема:

    SI4735
       ↓
    RDS decoder
       ↓
    RDS state
       ↓
    UI

UI только отображает уже готовое состояние.

Это позволит одновременно:
- крутить tuning;
- принимать RDS;
- обновлять S-meter;
- отображать интерфейс;

без ощущения, что устройство "задумалось".

16. I2C

I2C является одним из ключевых кандидатов на оптимизацию.

Необходимо отдельно измерить:

    100 kHz
    400 kHz
    500 kHz

для:
- SI4735 commands;
- frequency tuning;
- OLED update;
- SSB patch.

Нельзя просто предположить, что максимальная частота безопасна для всех компонентов.

Но даже переход на стабильно работающие 400 kHz может дать заметный эффект.

17. ПОЛНЫЙ FRAMEBUFFER НЕ НУЖЕН

При 2 KB SRAM framebuffer 128x64:

    128 * 64 / 8 = 1024 bytes

съедает около половины всей RAM.

Поэтому правильнее:

    dirty regions
    +
    tile/page rendering

Например обновлять только:

    frequency region
    signal meter region
    status region
    overlay region

Это позволяет сделать быстрый UI без катастрофического расхода RAM.

18. ЦЕЛЕВЫЕ ПОКАЗАТЕЛИ НОВОЙ ПРОШИВКИ

Input latency:

    encoder -> visible change
    цель: < 20 ms

UI latency:

    button -> visible response
    цель: < 30 ms

Frequency commit:

    encoder burst -> SI4735
    ориентир: 30-70 ms после окончания burst,
    если немедленный commit не требуется.

S-meter:

    5-10 Hz

RDS:

    asynchronous update

EEPROM:

    write only after idle timeout
    и только изменившиеся данные.

Эти цифры являются проектными целями, а не уже измеренными характеристиками.

19. ЧТО ПОЛУЧИТ ПОЛЬЗОВАТЕЛЬ

При правильной реализации пользователь должен почувствовать:

- encoder реагирует сразу;
- частота меняется без рывков;
- SSB tuning плавный;
- кнопки реагируют мгновенно;
- меню не тормозит радио;
- RDS появляется самостоятельно;
- S-meter не мешает tuning;
- экран не мигает;
- настройки понятны;
- интерфейс не перегружен.

То есть пользователь не думает:

    "Как быстро работает ATmega328P?"

Он просто думает:

    "Этот приёмник приятно использовать."

И это является правильным критерием успеха.

20. ЧТО НЕ ИЗМЕНИТСЯ

Новая архитектура не создаст новых физических возможностей SI4735.

Останутся прежними:

- реальные RF возможности;
- полоса пропускания;
- ограничения DSP;
- возможности демодуляции;
- аппаратные ограничения I2C;
- ограничения ATmega328P;
- характеристики OLED.

Поэтому задача проекта — не обмануть аппаратные ограничения, а максимально эффективно использовать существующее железо.

21. ПРЕДЛАГАЕМАЯ АРХИТЕКТУРА

Логические компоненты:

    Input Core
        ↓
    Event / State
        ↓
    Radio Core <----> Hardware
        |
        +---- RDS
        +---- Tuning
        +---- BFO
        |
        v
    UI State
        ↓
    Dirty Renderer
        ↓
    OLED Driver

Дополнительно:

    Config / EEPROM
        ↑
    State changes

Главный loop:

    void loop()
    {
        inputTask();
        radioTask();
        rdsTask();
        uiTask();
        storageTask();
    }

Все задачи:
- non-blocking;
- короткие;
- deterministic;
- без delay().

22. ПОРЯДОК РАЗРАБОТКИ

Не следует начинать непосредственно с дизайна UI.

Правильный порядок:

    1. Profiling
       ↓
    2. Radio Core
       ↓
    3. Timing / scheduler
       ↓
    4. Input Core
       ↓
    5. Display engine
       ↓
    6. UI design
       ↓
    7. Integration
       ↓
    8. Stress testing

Сначала необходимо измерить существующую систему, затем изменить архитектуру, и только после этого окончательно проектировать визуальный слой.

Иначе есть риск получить красивый UI, который съедает CPU, Flash и SRAM и в результате делает устройство медленнее.

24. ИТОГОВАЯ ОЦЕНКА КОНЦЕПЦИИ

Концепция новой архитектуры на старом железе технически реалистична.

Ожидаемый результат:

    Старое железо
          +
    новая архитектура ПО
          =
    значительно более отзывчивый приёмник

Не за счёт магического увеличения вычислительной мощности, а за счёт:

- уменьшения latency;
- устранения блокировок;
- оптимального планирования I2C;
- deferred hardware updates;
- event-driven input;
- dirty UI rendering;
- разделения Radio Core и UI;
- рационального использования Flash/RAM.

25. ФИНАЛЬНЫЙ ВЫВОД

Да, архитектурный скачок имеет смысл.

На существующем ATS-20 железе реально сделать устройство, которое субъективно ощущается как совершенно другое поколение.

При этом правильнее называть результат:

    "быстрый embedded SDR-подобный радиоприёмник"

а не полноценный широкополосный SDR.

Самое важное: потенциал улучшения находится не столько в добавлении функций, сколько в изменении поведения системы.

Цель новой прошивки:

    НЕ:
    "больше функций на одном экране"

    А:
    "каждое действие пользователя мгновенно,
     предсказуемо и понятно"

Именно это позволит получить устройство, которым приятно пользоваться даже при сохранении старого MCU, SI4735 и OLED.
