ATS-20 SSB — I2C burst и coalescing с deadline
Потенциальный выход, не текущий код. Ветка ATS-20Plus_next.
Опора: ATS-20_I2C_burst.txt (шум / 100 vs 400), этот файл (ощущение SSB tuning).
Сейчас в прошивке: desired частота уже в MCU (`g_currentFrequency` / `g_currentBFO`), OLED сразу,
Si473x через `FREQ_COMMIT_MS` 70. Шины 100 kHz. Постоянные 400 kHz не включать.

Главное

Скорость I2C ≠ скорость ощущения tuning.
400 кГц укорачивает транзакцию MCU → Si473x. На SSB пользователь слышит, как аудио
следует за пальцами. Ускорение шины трогает только один кусок этой цепочки.

Два разных rate, их нельзя склеить:

  UI  tuning rate  — как быстро OLED/состояние реагируют на энкодер (60–100+ Hz).
  RF  update rate  — как часто реально пишем частоту в Si473x (~50–100 Hz max).

Архитектурный вывод:

  ENCODER  (fast)
     │
     ▼
  UI STATE ──────────────► 60–100+ Hz   (каждый detent / burst тиков)
     │
     │ coalesce, latest value
     ▼
  RF SCHEDULER ──────────► ~50–100 Hz   (deadline, не debounce)
     │
     │ короткий пакет 400 kHz
     ▼
  Si473x

Покой: 100 kHz, CPU quiet, минимум poll, минимум OLED. Не цифровой генератор гармоник.

------------------------------------------------------------------------
1. Наивная петля (плохо)

  14.230.00 → 14.230.10 → 14.230.20 → …

  encoder → I2C → Si473x freq → wait → next encoder

На 100 кГц это слышно как затык. На 400 кГц транзакция короче, latency
encoder→чип меньше. Это всё ещё семь команд на семь тиков.

Правильнее: энкодер меняет локальный desired, не дёргает чип.

  ENCODER
     │
     ▼
  desired_freq     14 230 100
                   14 230 200
                   14 230 300
                   14 230 400
                          │
                          ▼
                    I2C scheduler
                          │
                          ▼
                       Si473x = latest

Быстрый спин +10×7 → desired = 14.230.700 → один burst → чип на 700.
Это важнее, чем «просто 100→400».

------------------------------------------------------------------------
2. Цепочка latency на SSB (четыре звена)

  Input        encoder → MCU
  Scheduling   MCU → старт I2C
  Chip         команда → смена демодулятора
  Perception   смена → слышимый результат

400 кГц улучшает только Scheduling (длину транзакции).
Не ждать «в четыре раза плавнее SSB» от одной смены clock.

------------------------------------------------------------------------
3. Coalescing vs deadline

Scheduler, например раз в ~10 ms, шлёт последнее актуальное:

  t=0     14.230000
  t=10    14.230700
  t=20    14.231500
  t=30    14.232400

Промежуточные значения исчезают. Для маленького DSP-приёмника это
не превращает I2C в мельницу цифрового мусора.

UI может рисовать каждый event:

  14.230.010  14.230.020  14.230.030  14.230.040   ← OLED сразу
  Si473x получает 14.230.040 одной транзакцией     ← RF latest

Это стыкуется с TRANSIENT: цифра живая, шина не мельтешит.

Опасность слишком агрессивного coalesce:

  encoder → display   прекрасно
  encoder → RF        ступеньками
  слух: «хррррр…» вместо прохода по SSB.

Поэтому deadline, не debounce.

  MAX_RF_LATENCY ≈ 10 ms

Можно сливать события. Нельзя позволять RF отставать от энкодера больше ~10 ms:

  events ──────────────────────>
  RF:     ↑         ↑         ↑
         10 ms     10 ms     10 ms

Debounce (как сейчас 70 ms: таймер сбрасывается на каждый тик) — наоборот:
чем быстрее крутишь, тем позже чип догоняет. Для SSB это хуже, чем
фиксированный потолок 10 ms.

Текущий `FREQ_COMMIT_MS` 70 — coalescing-debounce. Цель для SSB — coalescing-deadline.
70 ms оставить можно для AM/FM «серфинга», где слух не требует непрерывного BFO.

------------------------------------------------------------------------
4. Состояние шины: не 400 кГц всю сессию tuning

IDLE     100 kHz
   │ encoder starts
   ▼
TUNING   400 kHz только вокруг пакета commit (не «пока крутится — clock=400»)
   │ encoder stops
   ▼
SETTLE   сразу 100 kHz
   ▼
IDLE     quiet: SQL/S-метр редкие, OLED по dirty, sleep MCU

Сессия крутилки — временное high-performance окно, которое пользователь сам открыл.
Отпустил: 400→100, меньше poll, меньше refresh. Радио снова в тихой среде.

Не держать 400 кГц десятки ms «на всякий случай» после последнего тика.

C-функции (когда дойдём), не класс: `i2cFast()` / `i2cQuiet()` вокруг
`commitRadioFrequency` / `updateBFO` / `setFrequency`. Фон SQL/S-метр fast не включают.
См. ATS-20_I2C_burst.txt.

------------------------------------------------------------------------
5. Acceleration шага (отдельно от I2C)

Три скорости по скорости изменения энкодера (не «абсолютные rpm в вакууме»):

  одиночный click / медленно   10 Hz / detent
  быстрее                      100 Hz / detent
  очень быстро                 1 kHz / detent

Тогда burst 400 кГц особенно полезен: один commit несёт крупный скачок desired,
транзакция всё равно одна. Без acceleration быстрый спин на 10 Hz даёт либо
кучу мелких RF-апдейтов, либо (при debounce) длинную тишину и скачок.

Acceleration — UI/radio слой (`getSteps()` / burst `g_encoderCount`), не свойство I2C.
Сначала deadline+latest; acceleration — вторая итерация, avr-size.

------------------------------------------------------------------------
6. Что уже есть vs что писать

Есть:
  encoder first, OLED dirty, desired в RAM, фон I2C не на крутилке,
  SSB BFO + wrap kHz, патч 500 kHz уже burst.

Нет:
  400 kHz только на commit;
  deadline ~10 ms вместо reset-on-tick 70 ms (хотя бы в SSB);
  явный IDLE / TUNING / SETTLE для clock;
  velocity acceleration 10 / 100 / 1000.

Порядок, когда дойдём (после CW pitch по журналу, или раньше если SSB «тупой»):
  1. SSB: commit по max(10 ms с первого pending, не сброс на каждый тик)
     или periodic 10 ms пока `g_processFreqChange`.
  2. `i2cFast` только вокруг этого commit, сразу Quiet.
  3. Проверка слухом: слабый SSB на КВ, ДВ 9 кГц на idle vs spin.
  4. Acceleration — если остался flash и 10 ms всё ещё «ступеньки» на медленном шаге.

Не делать: постоянные 400; Settings «I2C 400»; RF=UI tick-for-tick;
RAII-класс ради скобок; coalesce без потолка latency.
